The PHI rule (computed, not hand-set)

A feature is PHI-eligible only when it is Generally Available and TRB-Approved. Private Preview & Beta carry no SLA and sit outside the compliance security profile — never PHI. Public Preview is production-capable but Databricks marks it subject to compliance restrictions, so it stays non-PHI / sandbox until the account team confirms coverage in writing.

Weekly refresh job built · schedule paused

A serverless Databricks Job (Asset Bundle in refresh-job/) is set to run Mondays 06:00 ET. The schedule is paused, so for now the job runs on demand. It reads the release-notes feed and workspace posture, updates Databricks phase (Axis A) in platform.feature_tracker.features, and republishes this page, so the tiles recompute from fresh data. It only reads TRB status (Axis B) and open TRB questions from the review register in platform.trb; it never writes them. Seven tasks: ensure_tables → ingest_feed → detect_changes → apply_changes → publish_site → publish_github, with snapshot_posture as a side branch that can't block publishing.

1 · Ingest the release feed

Pulls feed.xml (~30 items/week), dedupes, and drops model-catalog and version churn. Items on or before the baseline date (feed_baseline_date) count as already in the seed. Phase comes from the title ("is in Beta", "generally available"); "will soon" means Upcoming.

# preview locally, no workspace needed
python3 refresh-job/src/dry_run.py --days 7

2 · Match & read posture

Matches each item to a feature by name, then feed category, then an LLM (ai_query). A capability of a feature becomes a child row. Also snapshots compliance-security-profile and related settings.

3 · Apply safe changes, hold the rest

New features enter as Not Reviewed / Low. A change that would make a feature PHI-eligible (it reaches GA while TRB-Approved) is held for platform-team sign-off in proposed_changes. Losing eligibility applies at once (fail closed).

4 · Publish

Rebuilds this self-contained page from Unity Catalog with scripts/build_site.py (features, live TRB status, open TRB questions, and about 3 months of change history for the History button) and writes it to the site volume, plus a dated archive. publish_github then commits index.html to the public GitHub Pages repo; it skips cleanly if the GitHub token secret is missing. The team is emailed on success or failure.

5 · Monthly documentation check

A second job runs on the first Monday of each month, 07:00 ET (also paused for now): ensure_tables → check_docs → apply_doc_changes → publish_site → publish_github. It reads each feature's Databricks doc page, plus any dedicated limitations page it links to, and uses an LLM (ai_query) to extract the limitations that apply to that feature. The LLM is asked again only when the page text changes. Empty limitations are filled automatically; replacing text someone already wrote is held in doc_proposals for sign-off. A moved page updates the doc link; a dead link is held. Changes appear under History. It never writes phase or TRB status.
