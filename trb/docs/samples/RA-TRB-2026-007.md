# Security & Privacy (HIPAA) Risk Assessment – Mode: Databricks-to-Open

**Feature Name:** Mode: Databricks-to-Open (Data Sharing with Bearer Token / OIDC)  
**Review ID:** TRB-2026-007  
**Assessment Date:** August 11, 2026  
**Assessed By:** Privacy Officer  
**Overall Risk Level:** Moderate (mitigated to Low via conditions)  
**PHI-Eligible?** Conditional Yes (with BAA, token controls, and monitoring)

---

## 1. Executive Summary

Mode enables Databricks tables to be shared with external recipients (non-Databricks customers) via bearer token or OIDC authentication. Recipients access data via a web UI or API. Acme Health Plan proposes sharing member claims data with research organizations under Data Use Agreements (DUAs) and Business Associate Agreements (BAAs).

**Risk:** Bearer tokens can be compromised, exfiltrated, or shared. External recipients' security posture is unknown.  
**Mitigation:** Short token lifetime (≤30 days), IP allowlists, audit logging, BAA requirement, anomaly detection.

**With conditions, risk acceptable for PHI sharing with vetted partners.**

---

## 2. Risk Assessment Context

### 2.1 System Boundaries

**In scope:**
- Mode bearer token generation and validation
- External recipient's access to shared Databricks tables
- Query execution and result delivery to external recipient

**Out of scope:**
- External recipient's local security (data handling post-download)
- Mode infrastructure security (inherited Databricks/AWS controls)

### 2.2 Data Classification

**Data to Be Shared:** Member claims (medical claims, pharmacy, mental health), member demographics (age, region, diagnosis groupings—NOT names or SSN)  
**Sensitivity:** PHI (HIPAA-regulated); shared only under BAA with recipient  
**Volume:** Estimated 10M annual claims records for research partners  
**Recipients (Proposed):** 2–3 healthcare research organizations (universities, biotech firms)

## 4. Risk Analysis

### 4.1 Identified Risks

| # | Threat | Vulnerability | Likelihood | Impact | Risk Score | Mitigation |
|---|---|---|---|---|---|---|
| 1 | Bearer token exfiltrated (intercepted in transit / stolen from recipient's system) | Tokens are bearer credentials; no per-request signing or MFA | Medium | Critical | 12 | **COND-007-2:** Token lifetime ≤30 days; IP allowlist if recipient network known; rotate token quarterly |
| 2 | Bearer token shared with unauthorized third party | Mode doesn't prevent token sharing (stateless auth) | Medium | Critical | 12 | **COND-007-1 & 3:** BAA prohibits sharing; audit logs detect anomalies (e.g., queries from new IP); escalate |
| 3 | Recipient's system breached; attacker uses token for reconnaissance | Recipient may have weak security controls | Medium | High | 9 | **COND-007-1:** BAA includes security requirement (TLS, MFA, access logging at recipient). Acme requests evidence. |
| 4 | Query-pattern reconnaissance (e.g., repeated queries for rare disease counts) | Attacker learns member cohort sizes, infers identities | Low | Medium | 5 | **COND-007-3:** TRB flags queries with >10 results per 24hr; anomaly escalation threshold |
| 5 | Token accidental leak (e.g., logged in debug mode, pasted in chat) | No preventive control in Mode itself | Low | Critical | 5 | **COND-007-1:** Recipient training; BAA audit clauses |
| 6 | Insider (Acme employee) intentionally shares token | Requires deliberate bypass | Low | Critical | 5 | Standard access control + audit; escalate to CISO if detected |

### 4.2 Risk Mitigation (Conditions)

| Condition ID | Mitigation | Effectiveness |
|---|---|---|
| COND-007-1 | BAA signed before Mode token issued; BAA requires recipient to implement TLS, access logging, and not share token. Legal confirms BAA on file before provisioning. | High—legal obligation + verification |
| COND-007-2 | Bearer token lifetime ≤30 days; quarterly rotation. IP allowlist configured if recipient network IP known. Test token with test query before handoff. | High—limits exposure window & restricts source IPs |
| COND-007-3 | All Mode queries logged (recipient IP, query, result count, timestamp) to Databricks audit tables. Monthly anomaly review: >10 queries in 24hr, unusual IPs, abnormal result sizes flagged. 180-day retention. | Medium–High—enables detection & investigation |

## 5. Residual Risk Statement

**After conditions are met, residual risk is LOW.**

- **Token Compromise:** Mitigated by short lifetime (30 days) + IP allowlist + monitoring. Residual: Token compromised, used within 30 days without anomaly detection (low likelihood).
- **Recipient Breach:** Mitigated by BAA requirement + audit logging. Residual: Recipient breached, attacker queries undetected for days (very low due to monthly monitoring).
- **Insider Threat:** Standard access controls. Residual: Rogue employee intentionally leaks token (baseline security risk).

**Assumption:** Acme Health Plan maintains monthly audit review discipline. If reviews skipped or under-resourced, anomalies may go undetected (risk increases to Medium).

## 7. Compliance & Audit Notes

**Regulatory Framework:**
- HIPAA Privacy Rule § 164.504(e) (Business Associate Agreements): BAA mandatory before sharing PHI with external recipients
- HIPAA Security Rule § 164.312 (Technical Safeguards): Access controls, audit logging
- 45 CFR § 164.504(e)(2)(ii)(H) (Termination Clauses): Upon termination, recipient must return/destroy PHI

**Audit Trail Retention:**
- Mode query logs: 180 days (retained in Databricks audit tables)
- BAA documentation: 6 years (per HIPAA retention requirement)
- Anomaly detection reports: 1 year (per Acme policy)
